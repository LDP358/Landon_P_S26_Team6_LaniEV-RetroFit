SOLAR TRACKER DIGITAL TWIN — v1.9 | OUTER-RIM MOUNTS
==================================================
HOW TO RUN
1. Extract all .m files to the same folder.
2. Set the MATLAB Current Folder to that folder.
3. In the MATLAB Command Window:
      clear x_sensor_tracker_demo x_sensor_core tracker_config
      x_sensor_tracker_demo
4. Run geometric and tracking tests:
      verify_x_sensor_tracker

DESIGN GEOMETRY
- Panel size: 44 in East-West x 72 in North-South.
- Moving top frame: 12 in above the bottom frame when level.
- Central ball-joint pivot: 6 in above the lower frame plane.
- Top panel local mounting plane: 6 in above the ball joint.
- Each actuator: upper and lower pin at the EXACT corresponding outer
  rim midpoint, not an inward offset or internal cross-beam.
    North bottom: (0, +36, 0) inches.
    North upper:  (0, +36, +6) inches, relative to the ball joint.
    West bottom:  (-22, 0, 0) inches.
    West upper:   (-22, 0, +6) inches, relative to the ball joint.
- South and east two-link elbows retained (10 in per link, idealized).
- Each tilt axis has a +/-8-degree limit, including simultaneous tilt.
- X-cross sunlight direction sensor and GUI controls retained.

IMPORTANT: THESE ARE ENGINEERING TARGETS, NOT PART NUMBERS.
There is no confirmed conventional single-stage electric rod actuator that
provides an approximately 11.5-inch stroke from a 6.25-inch retracted
pin-to-pin length. Do not purchase based only on this virtual configuration.

The previously selected FIRGELLI C-Series FA-C-135-12-12 has a 16.5-inch
minimum retracted length and cannot fit between these aligned rim anchors.
The prior manufacturer current/force/power values are removed from this
version rather than incorrectly applying them to a hypothetical motor.

Physical design alternatives:
  A) Put lower end brackets roughly 10 in BELOW the lower rim (same x/y);
     the original 16.5–28.5-in actuators can meet the calculated range,
     but brackets and golf-cart space may make this unacceptable.
  B) Rework motion through a bell crank/linkage or other compact mechanism,
     then recompute actual actuator pin-to-pin lengths, stroke, force,
     speed, holding load and collisions.
  C) Raise frame gap by roughly 10 in and retain aligned outside mounts;
     this may be impractical on a golf cart.

MECHANICAL CAVEATS
- All linkages in the simulation are ideal line segments, NOT mechanical CAD.
- Hinge axes, body and linkage collisions, yaw restraint, wind-induced loads,
  bolt/stiffener dimensions and physical limit switches are unverified.
- The two freely folding elbows should not be assumed to prevent yaw.
- No current or energy predictions are possible without a real drive choice.
- Verify bottom clearance and structural stability before construction.


V2.0 ADDITION: CALCULATED ACTUATOR FORCE AND EXAMPLE CURRENT
----------------------------------------------------------
The GUI's lower row has three history charts: sensor imbalance, signed
quasi-static gravitational force on each actuator (lbf), and illustrative
motor running current (A). The status box shows values for the current
panel pose. EXPORT CSV includes force, current and cumulative energy.

With the ball joint as origin and the upper center-of-mass point 6 inches
above it, total moving assembly weight is 55 lbf:
    M_gravity = cross(R * [0;0;h_CG], [0;0;-55*4.448221615])
Each upper actuator's mounting pin is at R*upperMount, with force along the
line from its fixed lower pin to the rotated upper pin. The required axial
forces are found by simultaneously balancing X and Y gravitational torques:
    [M_Nx M_Wx; M_Ny M_Wy] * [F_N;F_W] = -M_gravity(1:2)
Signed axial force: + means EXTENDING force, - means COMPRESSIVE force.
This is quasi-static force under GRAVITY ONLY. No acceleration, friction,
wind, or forces generated by folding elbow linkages are included. The
model returns a residual YAW torque which would need resisting via a
properly engineered constraint; no such constraint has been validated.

Example running-current model for a NON-SELECTED virtual mechanism:
    P_mech = |F_axis| * |actuator linear speed|
    I_example = I_no_load + P_mech / (eta_drive * V)
This calculation runs only when an actuator actually changes length.
V=12 V, I_no_load=1.0 A/actuator, eta_drive=0.35 are HYPOTHETICAL
placeholders: edit tracker_config.m once actual motor/gearbox/screw
specifications or manufacturer current-vs-load data become available.
Current is ZERO in the model while not moving: active electrical holding,
backdriving, start-up surge and coasting are unmodeled. Motor losses are
bracketed using |force*speed| even on gravity-assisted motion; no claim
of exact electrical power or current is made.

Accumulated battery energy uses an assumed 90% DC-DC efficiency:
    E_battery_Wh += (I_N+I_W)*12*dt/(3600*0.9)
This is illustrative; do not select protection or wire gauge from it.

To query the forces directly from MATLAB:
    cfg = x_sensor_core('config');
    load = x_sensor_core('forces',deg2rad([8;8]),cfg);
    fprintf('North %.3f lbf, West %.3f lbf\n',load.forceLbf);
Then run verify_x_sensor_tracker before using results in the report.



V2.1 ELECTRICAL PLOT CORRECTION — ASSUMPTIONS, NOT MEASUREMENTS
-------------------------------------------------------------
Why Version 2.0 looked like a 0/1 A switch:
The virtual geometry puts a small gravity-only force on each actuator.
For an illustrative 8 deg pitch + 8 deg roll pose, that is about 1.32 lbf
(North) and 2.15 lbf (West). At the assumed 0.30 in/s travel speed
and assumed 35% efficiency, gravity adds only about 11 mA / 17 mA
to the ASSUMED 1 A unloaded running current. Plotting 0, 1.011 A,
and 1.017 A at ordinary axis resolution looks almost binary.

The simulation now distinguishes THREE electrical current components:
  1. Assumed ON-state no-load current (cfg.assumedNoLoadCurrentA)
  2. Load-induced current while moving (gravity only):
       deltaI = abs(gravityForceN)*actSpeedMps /
                (assumedDriveEfficiency*assumedMotorVoltageV)
  3. Short assumed STARTUP transient added when a motor initially starts
     or reverses direction (cfg.assumedStartExtraCurrentA and
     cfg.assumedStartDurationSec).

Instead of assuming the motors run continuously for every whole controller
interval, the code uses the actual displacement to calculate movement
time during each step. The main current traces are STEP AVERAGES, taking
into account the motor's ON fraction. The dotted traces are illustrative
PEAK currents, which are not resolved by the 0.20 s time-step.

With the original assumptions, e.g., at 8/8 deg, the theoretical steady
moving current is 1.011 / 1.017 A. If the motors start at the beginning
of a full 0.20 s simulation step, the extra 1.5 A surge for 0.08 s raises
the STEP-AVERAGE to about 1.611 / 1.617 A. An illustrative instantaneous
peak would be 2.511 / 2.517 A.

DEFAULT RESTING CURRENT IS ZERO:
Zero current only represents an UNPOWERED motor driver. It does not
prove the motor can hold a load without backdriving. Set
cfg.assumedHoldCurrentA if a selected driver ACTUALLY keeps the motor
electrically energized to hold position. Do not use an arbitrary hold
current to mask missing mechanics.

To adjust the example parameters in tracker_config.m:
    cfg.assumedNoLoadCurrentA = [1.0;1.0];
    cfg.assumedStartExtraCurrentA = [1.5;1.5]; % 0 disables surge
    cfg.assumedStartDurationSec = 0.08;       % seconds
    cfg.assumedHoldCurrentA = [0;0];         % off = zero current
    cfg.assumedDriveEfficiency = 0.35;
    cfg.assumedMotorVoltageV = 12.0;

The GUI now includes solid STEP-AVERAGED and dotted PEAK current plots.
Status shows current to three decimal places and load-related additions
in milliamps. CSV export includes these traces, startup contribution,
load contribution, and movement duty fraction.

WARNING: ALL ELECTRICAL INPUTS REMAIN HYPOTHETICAL because there is
no identified compact actuator fitting the v1.9 direct-edge mount.
These curves cannot establish real startup peaks, battery drain, motor
protection ratings, active holding loads, or stopping behavior.
Real actuator electrical data or a calibrated current-vs-load curve
would be needed for a defensible current prediction.
